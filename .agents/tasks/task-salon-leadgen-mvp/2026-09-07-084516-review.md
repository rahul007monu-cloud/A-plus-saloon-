# Salon lead-gen MVP: static site + WhatsApp booking + owner dashboard

A single-location salon site that captures booking leads on a public landing page, persists them to the browser's `localStorage`, and delivers each one to the owner instantly via a prefilled `wa.me` click-to-chat message. A separate owner dashboard reads the same store to list, search, CSV-export, and reply to leads. The stack is dependency-free HTML/CSS/vanilla JS by design — the build environment blocks the npm registry and has no backend — and deploys to Vercel as static files. The approach directly satisfies the request: free lead generation (organic/SEO landing page), free messaging (WhatsApp click-to-chat, no Business API), web + mobile (responsive markup), one showroom, Vercel deploy.

**Watch for:** the public form and the dashboard must agree on the `localStorage` key and lead shape — they do (`aplus_salon_leads`, matching object) [confirmed]. The dashboard is entirely unauthenticated and device-local, which is an accepted MVP trade-off but has a real consequence for the owner's workflow [confirmed]. Service-card price/duration markup is built with `innerHTML` from config values [confirmed, low risk]. Popup-blocker fallback for the WhatsApp hand-off is present and correct [confirmed].

**Verdict**: APPROVED

## High-level view

The lead pipeline has one hard correctness requirement: the writer (`main.js`) and reader (`admin.js`) must share the same storage contract. They do — both use the key `aplus_salon_leads` and the same `{ id, name, phone, service, date, time, message, createdAt }` shape, with `service` stored as the config slug and resolved to a display name on both ends.

WhatsApp delivery is a client-side hand-off, not a guaranteed send. On submit the lead is persisted first, then `window.open` targets a `wa.me` URL with the message in `encodeURIComponent`. If the popup is blocked the code detects it and surfaces a visible fallback link, so a lead is never silently lost between "saved" and "sent."

All lead values render through `textContent` in the dashboard, so a customer cannot inject markup via their name or message. The one exception is the services grid, which uses `innerHTML` — but only with owner-authored config data, not user input.

The known gap is the dashboard's nature: it is unauthenticated and its data lives only in the browser that captured it. Anyone who reaches `admin.html` sees whatever leads that browser holds, and leads submitted from a customer's phone never appear on the owner's device — WhatsApp is the actual cross-device channel. This is documented and deliberate, but it defines the ceiling of the tool and the owner needs to understand it.

### The localStorage contract between form and dashboard

`main.js` builds a lead as `{ id, name, phone, service, date, time, message, createdAt }`, pushes it onto the array under `aplus_salon_leads`, and stores `service` as the config slug (`values.service` is the `<option value>`, which is `svc.id`). `admin.js` reads the same key and resolves `service` back to a display name via `serviceNameById`, falling back to the raw id. Both sides return `[]` on corrupt or non-array JSON, so a corrupted store degrades to "no leads" rather than throwing.

Because `service` is stored as the slug, renaming or removing a service in `config.js` later will make old leads fall back to showing the bare slug in the dashboard and CSV — historical leads are only as readable as the current config.

### WhatsApp hand-off and the popup-blocked path

`saveLead` runs before `window.open`, so a blocked or failed popup never costs the lead. The `wa.me` URL is built from `ownerWhatsApp` stripped to digits, with the message passed through `encodeURIComponent` — newlines, `₹`, and free-text all encode safely. After opening, the code inspects the returned handle (`!popup || popup.closed || typeof popup.closed === "undefined"`) and, when blocked, un-hides and emphasizes a fallback anchor pointing at the same URL — the right failure mode for a feature browsers routinely block [confirmed].

### XSS safety in the dashboard

Every lead field originating from customer input reaches the DOM through `textContent` — the `el()` helper assigns `node.textContent`, and the phone/tel cells set `.textContent` explicitly. A customer submitting `<img onerror>` as their name renders as inert text. CSV export quotes every field and doubles embedded quotes; CSV formula-injection (a leading `=`/`+`/`-`/`@`) is not neutralized, but for a single-owner salon exporting their own leads this is negligible and out of scope.

The lone `innerHTML` on the render path is `service-card__meta` in `main.js`, interpolating `currency(svc.priceFrom)` and `svc.durationMins`. These are owner-authored config numbers, so there is no live injection vector — the Issues note is about future-proofing if services ever become user/remote data.

### Dashboard trust boundary and data locality

The dashboard ships no authentication — `admin.html` is a static file served to anyone who requests it. `robots.txt` disallows it and the page carries `noindex, nofollow`, which keeps it out of search indexes but is explicitly not an access control; the URL is guessable. Leads live in the `localStorage` of whichever browser ran the booking form, so the dashboard only ever shows leads captured on that same device/origin — a customer booking from their own phone writes to their own browser, not the owner's. WhatsApp is therefore the real delivery channel and the dashboard is a device-local backup view. This is documented in the README's storage note and "Deferred / future phases," with the upgrade path (serverless API + hosted DB) spelled out — a bounded, disclosed limitation. Flagged so the reviewer confirms the owner's expectations match.

### Responsive rendering and accessibility

Both `#leads-table-wrap` and `#leads-cards` render from the same visible-leads set, toggling their `hidden` attribute on whether there are results; media queries then force `display:none !important` on the table below 768px and on the cards at/above it. The `[hidden]` rules also carry `!important`, so the empty/no-results states win regardless of breakpoint [confirmed]. The landing page has a skip link, a labelled mobile nav toggle wired to `aria-expanded`, `aria-live` error regions with `role="alert"`, `aria-required` on required inputs, a `focus-visible` outline, and a `prefers-reduced-motion` block. The honeypot is offscreen-positioned and `aria-hidden`, hidden from both sighted users and assistive tech while still catching bots. Mobile-first CSS with `600px`/`900px` breakpoints covers the "web + mobile dono" requirement.

### Validation and spam handling

Validation requires a name of ≥2 characters, a phone of 7–15 digits after stripping non-numerics, and a selected service; errors show inline and clear on input. The honeypot `company` field short-circuits submission silently when filled. The phone check is intentionally loose to accommodate international formats — proportionate for a client-only lead form with no server to enforce anything.

### SEO and deploy configuration

`robots.txt` allows the site and disallows `/admin.html`; `sitemap.xml` lists only the public home page; `admin.html` additionally carries `noindex, nofollow` — the private page is excluded three ways. JSON-LD (`HairSalon`), Open Graph, and Twitter card tags are present on the landing page. `vercel.json` is valid, enables clean URLs, and sets `nosniff`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy` headers. The placeholder domain `a-plus-salon.example.com` appears in the canonical link, `og:url`, JSON-LD `url`/`image`, sitemap `<loc>`, and the robots `Sitemap:` line and must be replaced at deploy (called out in the README).
